# VDR110. Scenario subject should be unique
A subject is the scenario name shown in the report and the key used by `vedro run --subject`. When two scenarios declare the same subject, the report gets indistinguishable entries and `--subject` selects both of them instead of one.

Unlike VDR106 (several `subject` assignments inside one scenario), this rule compares subjects across all scenarios in the `scenarios/` folder.

### ❌ Anti-pattern
```python
# scenarios/auth/register_user.py
class Scenario(vedro.Scenario):
    subject = "register new user"

    def when_user_registers(self):
        self.response = ...


# scenarios/profile/create_profile.py
class Scenario(vedro.Scenario):
    subject = "register new user"   # VDR110

    def when_user_registers(self):
        self.response = ...
```

### ✅ Best practice
```python
# scenarios/auth/register_user.py
class Scenario(vedro.Scenario):
    subject = "register new user"

    def when_user_registers(self):
        self.response = ...


# scenarios/profile/create_profile.py
class Scenario(vedro.Scenario):
    subject = "create profile for registered user"

    def when_user_creates_profile(self):
        self.response = ...
```

### ⚠️ Exception

Subjects are compared as literal strings, so parametrized subjects are compared by their template, not by the names they get at runtime:

```python
# scenarios/get_names_by_error.py
class Scenario(vedro.Scenario):
    subject = "get names with {error}"

# scenarios/get_names_by_locale.py
class Scenario(vedro.Scenario):
    subject = "get names with {locale}"   # not an error
```

These two are not reported, two identical templates are.

This is a limitation of static analysis, not a decision about what is duplicated: vedro renders a subject as `subject.format(**params)`, and parameter values are not known before the run - they can be generated or random. So a parametrized scenario can still collide with another one in the report and stay unreported here, for example `"register {role}"` with `@params("admin")` against a plain `"register admin"`.

A subject with a `{subject}` placeholder takes its name from params, so it is never compared, even with an identical template:

```python
# scenarios/delete_reaction_on_moderated_photo.py
class Scenario(vedro.Scenario):
    subject = "delete reaction on {subject} photo by author"

    @params("premoderated")
    @params("postmoderated")
    def __init__(self, subject): ...

# scenarios/delete_reaction_on_hidden_photo.py
class Scenario(vedro.Scenario):
    subject = "delete reaction on {subject} photo by author"   # not an error

    @params("rejected")
    @params("hidden")
    def __init__(self, subject): ...
```

The same goes for a subject that is a placeholder only, `subject = "{subject}"`.

A subject that is not a string literal (a variable, an f-string, a concatenation) cannot be compared either and is skipped.

### How it works

Unlike other rules, VDR110 reads the whole `scenarios/` folder, not only the file being checked. The folder is looked up from the file being checked, so in a monorepo every `scenarios/` folder is a separate namespace and identical subjects in different services are not reported.

Of the scenarios sharing a subject, the first one by sorted path is left alone and every other one is reported, pointing at the first. This keeps the result the same under any `--jobs` setting.
